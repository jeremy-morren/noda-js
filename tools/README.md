# .NET Tools

Two projects, built with the exact .NET SDK in `global.json`:

- `NodaJs.Package` makes the single-file module's release archives (`zip` and `tar-gzip` commands), reproducibly:
  the same files and time give the same bytes on every OS. `npm run build:module` (`scripts/build-module.ps1`) runs
  it.
- `NodaJs.Tools`, described below.

A .NET tool (`NodaJs.Tools`, one project with a command per kind of output) that takes everything noda-js can get
from .NET and NodaTime, and writes it into the repo as TypeScript. Every file they write is named `*.generated.ts` and starts with an `<auto-generated>`
header that records the NodaTime, .NET and ICU versions it came from. Don't edit those files; re-run:

```powershell
pwsh -NoProfile -ExecutionPolicy Bypass -File tools/generate.ps1                 # everything
pwsh -NoProfile -ExecutionPolicy Bypass -File tools/generate.ps1 -Only scenarios
```

`generate.ps1` publishes `NodaJs.Tools` to `tools/publish/` and runs one of its commands (`data`, `cldr`,
`scenarios`, or `all`); run the published tool with `--help` for its options. Command-line parsing uses
System.CommandLine.

Building `NodaJs.Tools` first clones NodaTime at the version (and tag) `NodaTimeVersion` in
`Directory.Packages.props` into `.nodatime/<version>/` (gitignored), with its `PrepareNodaTime` target. The tool
references NodaTime's projects from that clone, so they always describe exactly the code we port.
The runtime is pinned too: the tools run on exactly the runtime `global.json`'s SDK ships with.
ICU is pinned (app-local `Microsoft.ICU.ICU4C.Runtime`, `IcuVersion` in `Directory.Build.props`), so
culture data is the same on every OS. Re-running is idempotent: unchanged files aren't rewritten.

| Command     | Writes              | From |
|-------------|---------------------|------|
| `data`      | `src/noda-js/**/*.generated.ts` enums (with doc comments), `src/noda-js/NodaConstants.generated.ts`, `src/noda-js/Text/TextErrorMessages.generated.ts`, `src/noda-js/Cultures/<name>.generated.ts` (cultures in `cultures.txt`), invariant culture + NodaTime `PatternResources`, `src/noda-js/TimeZones/TzdbBundledData.generated.ts` (and `test/fixtures/tzdb/tzdata<version>.tar.gz`), `test/api/nodatime-api.generated.ts`, `test/golden/**` | Reflection over NodaTime; .NET `CultureInfo`; NodaTime's `TzdbCompiler`; NodaTime itself formatting values |
| `cldr`      | `src/noda-js/Bcl/CldrWindowsZones.generated.ts` | CLDR `windowsZones.xml` (latest release), parsed by NodaTime's `CldrWindowsZonesParser` |
| `scenarios` | `test/scenarios/**` | Every NUnit test case in `NodaTime.Test` and `NodaTime.TzdbCompiler.Test`, enumerated by NUnit itself |
| `system-zones` | `test-results/system-zones.json` (not committed: it's the machine's) | NodaTime's `BclDateTimeZoneSource` on this machine: IDs, system default, every zone's names, `TimeZoneInfo` rules and zone intervals (1800-2100), the local zone, and .NET's IANA → Windows ID conversions. Run by `scripts/export-system-zones.ps1`; `test/system/WindowsComparison.test.ts` compares noda-js/system with it |

## tzdb

By default the bundled tzdb is compiled by NodaTime's own `TzdbCompiler` from the latest IANA release
(`tzdata-latest.tar.gz`) and the latest CLDR `windowsZones.xml`, so a new tz release doesn't need to
wait for nodatime.org. (For the same inputs the result is byte-identical to nodatime.org's NZD.)
`-Tzdb latest` bundles nodatime.org's published file instead; `-Tzdb embedded` uses the copy inside the
pinned NodaTime (offline). `-Tzdata` and `-Cldr` pick specific input releases.

When it compiles, `data` also saves the tzdata tarball it compiled, byte for byte as downloaded, to
`test/fixtures/tzdb/tzdata<version>.tar.gz` (deleting any other `tzdata*.tar.gz` there, so there's always exactly
one), so a test can compile the same input with noda-js's own compiler and compare its NZD with the bundled one.
The Windows mapping in the bundled NZD is the same CLDR `windowsZones.xml` that `cldr` exports (both take the latest
CLDR release unless `-Cldr` says otherwise), so the two match as long as `data` and `cldr` run together.

## Test scenarios

The `scenarios` command loads `NodaTime.Test.dll` and `NodaTime.TzdbCompiler.Test.dll` into NUnit's
`DefaultTestAssemblyBuilder`, so the cases are exactly what NUnit runs: `[TestCase]`, `[TestCaseSource]`, `[Values]`,
inherited tests (e.g. `PatternTestBase<T>`), `ExpectedResult`, ignore/explicit state. Each fixture becomes
`test/scenarios/<namespace path>/<Fixture>.generated.ts` (`NodaTime.Test.Text.LocalDatePatternTest` →
`Text/LocalDatePatternTest.generated.ts`; the compiler's tests go under `TzdbCompiler/`, so
`NodaTime.TzdbCompiler.Test.Tzdb.TokensTest` → `TzdbCompiler/Tzdb/TokensTest.generated.ts`, ported in
`test/ported/TzdbCompiler/Tzdb/TokensTest.test.ts`), all listed in `test/scenarios/index.generated.ts` by NUnit full
name: every test method with its C# source location
(from the PDB), parameters, and cases with arguments encoded as tagged values (see
`NodaJs.Tools/Common/TsValueEncoder.cs` and `test/helpers/decode.ts`). Cultures the cases use, including
NodaTime.Test's custom test cultures, go to `test/scenarios/cultures.generated.ts`.

Bump `NodaTimeVersion` in `Directory.Packages.props` (Dependabot proposes it) and re-run to pick up new upstream tests; they appear in vitest as `todo`
until ported. Fixtures whose data depends on the host (OS time zones, the current time) or that are out
of scope are listed in `scenario-exclusions.txt`; they're still emitted, with their test names, but
without cases.

## Windows time zones

The `cldr` command exports only CLDR's Windows ↔ tzdb ID mapping (Unicode License). Windows' own
zone rules exist only in a Windows machine's registry, with no published, redistributable source, so
nothing exports them: `noda-js/system` reads them from the machine it runs on (as .NET's `TimeZoneInfo` does), and
`noda-js/windows` maps Windows zone IDs to tzdb zones elsewhere. The `system-zones` command exports what NodaTime sees
on the machine it runs on, only to test against (see [docs/Timezones.md](../docs/Timezones.md)).
