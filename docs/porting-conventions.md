# Porting conventions

noda-js is a **file-by-file port of NodaTime** (pinned version `NodaTimeVersion` in `tools/Directory.Packages.props`,
cloned into `.nodatime/<version>/` when `tools/NodaJs.Tools` builds). The aims, in order:

1. **Same API as NodaTime, with the same names** (PascalCase, as in C#). A C# *property* is a TS *getter*
   (`duration.TotalSeconds`, `date.Year`, `Instant.MaxValue`); a C# *method* is a TS method
   (`date.PlusDays(1)`, `instant.ToUnixTimeSeconds()`). Only members JS itself calls by name keep their JS
   names: `toString`, `toJSON`/`fromJSON`, `valueOf`, `[Symbol.iterator]`, and the members of built-in types a
   class extends (`Error.message`, `Map.get`).
2. **Same wire formats**: text patterns, `toString()`, and JSON (`toJSON()`/`fromJSON()`) produce and
   accept exactly what NodaTime does.
3. **As little of our own code as possible.** Translate NodaTime's code line by line; don't redesign it.
   Anything .NET can tell us by reflection (enums, constants, error messages, culture data, tzdb, the
   public API shape, test cases) is generated by the tools in `tools/` instead of being written by hand.

## Files

| NodaTime | noda-js |
|---|---|
| `src/NodaTime/Foo.cs` | `src/noda-js/Foo.ts` |
| `src/NodaTime/Text/Patterns/Bar.cs` | `src/noda-js/Text/Patterns/Bar.ts` |
| `src/NodaTime.Testing/...` | `src/noda-js/Testing/...` |
| `src/NodaTime.Test/FooTest*.cs` (all partial files) | `test/ported/FooTest.test.ts` |
| anything generated | `*.generated.ts` next to where the C# lives. **Never edit these**; re-run `tools/generate.ps1`. |

One TS file per C# type (partial classes are merged into one file). Keep NodaTime's member order and
`#region`s (as `// #region` comments) so files can be compared side by side with the C#.

Every hand-ported file starts with:

```ts
// Ported from NodaTime 3.3.7: src/NodaTime/LocalDate.cs
// Copyright 2009 The Noda Time Authors. All rights reserved.
// Use of this source code is governed by the Apache License 2.0,
// as found in the LICENSE.txt file.
```

noda-js's own code (in its own files: ported files only get small, commented additions) starts with
`// noda-js: new code.` and what it is for. Code ported from .NET itself (only `src/noda-js/System/`: the parts of
`System.TimeZoneInfo` and `System.DateTime` that NodaTime's `BclDateTimeZone` uses, for `noda-js/system`) starts with
`// noda-js: port of <what> from dotnet/runtime (<path>).` and `// Copyright (c) .NET Foundation and Contributors. Licensed
under the MIT license (see NOTICE.txt).`, and follows the same rules: line by line, the .NET names and comments.

Keep NodaTime's XML doc comments, converted to JSDoc (`<summary>` text becomes the description,
`<param>` → `@param`, `<returns>` → `@returns`, `<exception cref="X">` → `@throws {XError}`,
`<see cref="Foo.Bar"/>` → `{@link Foo.Bar}`). Keep implementation comments verbatim.

## Imports and module cycles

NodaTime's types reference each other freely, which in ESM means import cycles. Two rules make
cycles harmless:

1. **Inside `src/`, import other NodaTime types from the barrel `src/noda-js/internal.ts`** (e.g.
   `import { Duration, Preconditions } from "./internal.ts"`), never from each other's files. The barrel
   lists modules in a safe evaluation order (base classes before subclasses). Leaf modules that import
   nothing from the barrel (generated constants, `Utility/` helpers) may be imported directly.
   Code in a separate entry point (`src/noda-js/TimeZones/Tzdb...`, `src/noda-js/System/`, `src/noda-js/Testing/`) imports core
   from `internal.ts` too, and must not be added to it.
2. **No module-level code may use another module's exports at evaluation time**, except `extends`
   (handled by the barrel order) and leaf modules. In particular C# `static readonly` fields and
   static properties of object type become **lazy static getters**:

   ```ts
   // C#: public static Instant MaxValue { get; } = new Instant(...);
   static get MaxValue(): Instant { return (maxValue ??= new Instant(...)); }
   ```
   with `let maxValue: Instant | undefined;` at module level. (If C# returns a new struct each time,
   `=> new X(...)`, a plain getter without caching is fine.) Primitive constants stay
   `static readonly X = 5;`. This also keeps everything tree-shakable (`"sideEffects": false`).

Use `import type` for type-only imports. Relative imports use `.ts` extensions (`import { Duration } from "./internal.ts"`); `tsc` rewrites them to `.js` on emit (`rewriteRelativeImportExtensions`).

## Types and members

| C# | TypeScript |
|---|---|
| `struct` / `class` | `class`; fields `readonly` where C# has `readonly`. Private/internal fields use TS `private`/plain fields (not `#private`), so internal factories can create instances. |
| Type names | Unchanged (`LocalDate`, `ZoneInterval`, `IPattern<T>`). Interfaces keep the `I` prefix. |
| Members (public, internal **and** private methods/properties) | **The C# name, unchanged**: `PlusDays`, `MaxValue`, `ToUnixTimeMilliseconds`, `BclCompatibleTicks`. Exceptions, because JS calls them by name: `toString`, `toJSON`/`fromJSON`, `valueOf`, `[Symbol.iterator]`, and members overriding a built-in type's (`Error.message`/`name`, `Map.get`/`set`/`has`/`delete`/`clear`). C# indexers (`this[...]`, which have no name in C#) are `Get(key)`/`Set(key, value)`. |
| Enum members | **Unchanged** (`IsoDayOfWeek.Monday`, `PeriodUnits.Years`). Enums are generated. |
| Property (instance or static) | getter (`get year(): number`), never a method. Settable properties of NodaTime classes (only `PeriodBuilder`) get getter + setter. |
| Method | method |
| Field | C#'s `_camelCase` convention: a field that is camelCase in NodaTime (private, or internal like `TzdbStreamData.Builder.stringPool`) is `_camelCase` (`_nanoOfDay`, `_localDate`), whether or not TS needs it to be non-`private` (the `Object.create` factories assign fields directly). A field standing in for a C# property, or a field NodaTime itself names in PascalCase (`static readonly`, the parse buckets' `TemplateValue`), is PascalCase. Module-level `let` caches behind lazy getters (`let maxValue`) are plain camelCase locals, not fields. |
| `const` | `static readonly` with the C# name, or a module-level `const` (keep the C# name) if private. |
| Public constructor overloads | one `constructor(...args)` that dispatches on argument count/types at runtime, with TS overload signatures. |
| Internal/private constructors | `/** @internal */ static` factory methods named **`New` + the C# parameter names, each capitalised, concatenated**: `internal LocalDate(int daysSinceEpoch)` → `LocalDate.NewDaysSinceEpoch(daysSinceEpoch)`; `internal LocalDate(YearMonthDayCalendar yearMonthDayCalendar)` → `LocalDate.NewYearMonthDayCalendar(ymdc)`; `private Duration(int days, long nanoOfDay, bool noValidation)` → `Duration.NewDaysNanoOfDayNoValidation(...)`. This rule is mechanical on purpose: files ported separately must agree on these names. The factory may build the instance with `Object.create(X.prototype)` and assign fields, or call the constructor with a module-private token. |
| Nested types (`OffsetDateTime.Comparer`, `ZoneEqualityComparer.Options`) | A top-level class/enum named `OuterInner` (`OffsetDateTimeComparer`), declared before `Outer` in the same file (generated enums live in their own file), plus `static readonly Inner = OuterInner;` on `Outer` so `OffsetDateTime.Comparer.Local` works as in C#. |
| `default(T)` for a NodaTime struct | Whatever value the C# default is (e.g. `Duration.Zero`, `LocalDate` 0001-01-01). If code needs it and NodaTime has no named property, add `/** @internal */ static get DefaultValue()`. |
| `struct` field of a NodaTime struct type (e.g. `LocalDateTime.date`) | Plain readonly field holding the instance (values are immutable, so sharing is safe). |
| Method overloads | one implementation with TS overload signatures and runtime dispatch. If two overloads can't be told apart at runtime (e.g. both take one `number`), keep the more common one under the C# name and give the other a suffixed name; list it in `docs/api-differences.md`. |
| Static methods | static methods (C# name). |
| `out` parameters | Return a tuple `[result, outValue]` (internal code), or an object if there are several. |
| `ref` parameters | Return the new value, or pass a small mutable holder `{ value }`. |
| `T?` / nullable reference | `T \| null` (not `undefined`). Optional parameters with C# defaults: `param: T = default`. |
| Delegates (`Func<T, R>`, NodaTime delegates) | Function types (`(x: T) => R`). Named NodaTime delegate types become `type` aliases. |
| Functions | Every function is PascalCase, ported or not: C# extension methods (below), private static methods that became module-level functions (`GenerateTotalDaysByMonth`), and noda-js's own helpers (`PadStart`, `CreateReadOnlyMap`, `Int64.Add`). So are the members of objects standing in for C# static classes (`GregorianJulianCalendars.Gregorian`, `ZoneIntervalConstants.MarkerMinValue`) and the properties of data shapes (`CultureData.DateTimeFormat`, `WindowsZonesData.MapZones`). The only camelCase names are the JS protocol members above, instances such as `tzdb` and the cultures (`enAU`), and plain local variables. |
| Extension methods (`IsoDayOfWeekExtensions`) | Exported functions with the C# name (`ToDayOfWeek`, `InZone`) in the ported file. Where the target is a noda-js class, also add an instance method/getter that calls it. |
| `IEquatable<T>.Equals` / `object.Equals(object)` / `==` / `!=` | The class declares `implements IEquatable<T>` (internal interface in `Utility/Equality.ts`, never exported from an entry point) with two overload signatures and one implementation: `Equals(other: T): boolean; Equals(other: unknown): boolean; Equals(other: unknown): boolean { return other instanceof T && ...; }`. Always check `instanceof` before touching `other`'s fields, so `Equals(null / undefined / {} / another type)` is false and never throws. |
| `IComparable<T>.CompareTo` / non-generic `IComparable.CompareTo(object)` / `<` `<=` `>` `>=` | `implements IComparable<T>` (same file) with `CompareTo(other: T \| null): number; CompareTo(other: unknown): number;` and one implementation: `null`/`undefined` → `1`; anything that isn't a `T` → `Preconditions.CheckArgument(other instanceof T, "obj", "Object must be of type NodaTime.T.")` (C#'s message); then compare (cast with `other as T`). Only for types that are `IComparable` in C#. Also static `Compare(a, b)` only if NodaTime has one. Comparer classes (`IComparer<T>`/`IEqualityComparer<T>`, e.g. `OffsetDateTime.Comparer`) keep their `(x, y)` signatures but are also `instanceof`-safe. |
| `operator +` / `-` / `*` / `/` | static `Add` / `Subtract` / `Multiply` / `Divide` (NodaTime already has most of these as named statics; merge overloads). Instance `Plus`/`Minus`/etc. exist only where NodaTime has them. |
| unary `-` | static `Negate(x)` plus instance `Negate()` if NodaTime has one. Unary `+` is dropped. |
| implicit/explicit conversion operators | static `From...`/instance `To...` method named for what it converts; list in `docs/api-differences.md`. |
| `GetHashCode` | omitted. |
| `valueOf` | every value type defines `valueOf(): never { throw new TypeError(...) }` (via `Utility/ValueType.ts`), so `a < b` fails loudly. |
| `ToString()` | `toString()` — NodaTime's default pattern **with the invariant culture** (NodaTime uses the current culture; JS has none). |
| `ToString(string?, IFormatProvider?)` | `toString(patternText?: string \| null, formatProvider?: IFormatProvider \| null)` |
| `Deconstruct` | omitted (JS destructuring works on getters: `const { Year, Month } = date`). |
| `IXmlSerializable`, `TypeConverter`, BCL interop (`DateTime`, `TimeSpan`, `DateTimeOffset`, `DateOnly`, `TimeOnly`, `TimeProvider`, `Stopwatch`), `HighPerformance` | Not ported (listed in [api-differences.md](api-differences.md)). Leave a one-line `// Not ported: <member> (<reason>)` comment where the member was, so diffs against the C# stay readable. |

### JSON

Each value type gets `toJSON()` (what `NodaTime.Serialization.SystemTextJson` writes) and a static
`fromJSON(json)` (parse with the same pattern; throw `UnparsableValueException` on failure).

## Numbers

NodaTime is compiled with **overflow checking on** (`CheckForOverflowUnderflow`), so `int`/`long`
overflow throws `OverflowException` unless the code is in an `unchecked` block.

| C# | TypeScript |
|---|---|
| `int`, `short`, `byte` | `number`. Where overflow is reachable, check with `Int32.Checked(x)` (throws an `OverflowException`). `unchecked((int) x)` → `x \| 0`. |
| `int / int`, `long / long` | `Int64.Div(a, b)` / `Math.trunc(a / b)` (exact for safe integers). `%` is the same as C#. |
| `long` whose magnitude stays below 2⁵³ (nanosecond-of-day, days, milliseconds since epoch, seconds) | `number` |
| `long` that can exceed 2⁵³ (ticks since epoch, total nanoseconds, `Period` hour…nanosecond fields) | Internally: an exact **`Int64Value`** (`Utility/Numbers.ts`): a `number` when it's a safe integer (the common case, no allocation), otherwise a `Long` (the [long.js](https://github.com/dcodeIO/long.js) package). Compute with the checked `Int64` helpers (`Int64.Add`, `Subtract`, `Multiply`, `Divide`, `Remainder`, `Negate`, `Compare`, `Equals`, `ToString`), which throw `OverflowException` like checked C#; or split into days + remainder exactly as NodaTime does. In **API results**: plain `number`, the nearest double beyond 2⁵³ (`ToUnixTimeTicks(): number`, `BclCompatibleTicks`, `ToInt64Nanoseconds()`, `period.Hours`); keep an `/** @internal */` exact accessor where internal code needs the exact value (`ExactHours`, `ToInt64NanosecondsExact()`). In **API arguments**: accept `number \| string` and convert with `Int64.FromArgument(value, "name")`: a decimal string gives an exact value beyond 2⁵³ (`Duration.FromNanoseconds("9223372036854775807")`). Where a C# `double` overload exists too, a non-safe-integer `number` takes the `double` path. Internal callers may pass a `Long` through an `/** @internal */` overload (`PeriodBuilder.set`, `Instant.FromUnixTimeTicks`). |
| `BigInteger`, `Int128`, `decimal` used for wide arithmetic (only `Duration` beyond the `long` range of nanoseconds, about ±292 years) | `WideInteger` (`Utility/WideInteger.ts`), a small exact integer used only on those rare paths. Reproduce `decimal` semantics where they show (96-bit overflow → `OverflowException`, rounding of division results). Members that exist only for `BigInteger`/`Int128` are not ported. |
| `double` | `number` |
| `char` | `string` of length 1; char arithmetic via `charCodeAt`. |
| `bool` | `boolean` |

**No `BigInt` anywhere in `src/`** (no `bigint` type, `BigInt(...)` or `123n` literal): the runtime baseline is
**ES2015** (Chrome 51, Firefox 54, Safari 10, Edge 15). `tsconfig.json` targets ES2015 with the ES2015 library (plus the
`Intl` typings that `src/noda-js/System` feature-checks), so `tsc` rejects later runtime APIs; use the helpers in `src/noda-js/Utility`
instead (`PadStart`/`PadEnd` from `Utility/StringPadding.ts`, `indexOf` for array `includes`, `Object.keys` for
`Object.entries`). Tests run on Node and use `test/tsconfig.json` (newer library, Node types); `npm run typecheck`
checks both. Generated source must follow the same rule (`Ts.SourceInt` in the tools); generated test data may use
`bigint` literals, which `test/helpers/decode.ts` turns into what the API accepts.

## Exceptions

Every error noda-js throws for a NodaTime exception is a `NodaError` (`src/noda-js/Utility/NodaError.ts`). Its `Codes`
are the .NET exception type's name (also the error's `name`), then its base types' names, nearest first, without
`Exception` (the base of every exception): `["SkippedTimeException", "ArgumentOutOfRangeException",
"ArgumentException", "SystemException"]`. It's never empty, and it's a literal tuple type for each type.
`IsNodaError(e, code)` is true if `Codes` includes `code`, as a C# catch clause catches a type and the types derived
from it. The hierarchy is `BaseCodesByCode` in `NodaError.ts`.

- **The .NET library's exceptions** (`ArgumentException`, `ArgumentNullException`, `ArgumentOutOfRangeException`,
  `InvalidOperationException`, `OverflowException`, `DivideByZeroException`, `NotSupportedException`,
  `NotImplementedException`, `FormatException`, `KeyNotFoundException`, `IndexOutOfRangeException`,
  `InvalidCastException`, `InvalidDataException`, `HttpRequestException`, `TimeZoneNotFoundException`,
  `InvalidTimeZoneException`) are **types,
  not classes**, in `src/noda-js/Utility/SystemExceptions.ts`: a `NodaError` with that code (or a derived one), plus
  the .NET type's own members (`ParamName`, `ActualValue`, `StatusCode`). Ported code creates them with that file's
  internal factories, which take the .NET constructor's parameters: `throw new ArgumentOutOfRangeException(nameof(x),
  x, msg)` → `throw NewArgumentOutOfRangeException("x", x, msg)`. Code catching them uses `IsNodaError(e,
  "FormatException")` for `catch (FormatException)`.
- **NodaTime's own exceptions** are classes derived from `NodaError`, with their own code and properties
  (`UnparsableValueException.Value`, `SkippedTimeException.Zone`, ...); their `Codes` continue with NodaTime's base types
  (`SkippedTimeException` and `AmbiguousTimeException` also have `ArgumentOutOfRangeException`'s `ParamName` and
  `ActualValue`). They are `UnparsableValueException`, `InvalidPatternException`, `SkippedTimeException`,
  `AmbiguousTimeException`, `DateTimeZoneNotFoundException`, `InvalidNodaDataException`,
  `InvalidDateTimeZoneSourceException` (and the internal `MissingTokenException`, `DebugPreconditionException`).

Tests check the exact code (the first of `Codes`), as NUnit's `Assert.Throws<T>` checks the exact type: `assertThrows("ArgumentException",
action)`, `expect(action).toThrowNodaError("FormatException")` (also with `.rejects`), and
`expect(error).toBeNodaError("InvalidOperationException")` (`test/setup.ts`).

## .NET library shims

Ported code uses a few .NET library types. Small shims keep the ported code close to the C#:

| .NET | Shim |
|---|---|
| `StringBuilder` | `Utility/StringBuilder.ts` (`Append`, `Insert`, `Length` get/set, `toString`) |
| `string.Format(fmt, args)` / `Invariant($"...")` | `FormatString(fmt, ...args)` in `Utility/StringFormat.ts` / template literals |
| `int.ToString("D2", InvariantCulture)` etc. | `FormatHelper` (ported) |
| `CultureInfo` (as `NodaCultureInfo`), `DateTimeFormatInfo`, `CompareInfo`, `IFormatProvider` | `Globalization/NodaCultureInfo.ts`. Culture data is generated by `tools/NodaJs.Tools (data)` into `src/noda-js/Cultures/*.generated.ts`; `NodaCultureInfo.InvariantCulture` is in core. |
| `IReadOnlyList<T>` / `IList<T>` / arrays | `readonly T[]` / `T[]` |
| `IDictionary`, `IReadOnlyDictionary` | `ReadonlyMap` / `Map` |
| `IEnumerable<T>` with `yield` | generator functions returning `Iterable<T>` |
| `ConcurrentDictionary` | `Map` |
| `Lazy<T>` | a lazily set field |
| `Debug.Assert`, `Preconditions.Debug*` | Kept as calls, but no-ops, as in a NodaTime release build (so ported tests use the release-build variants, e.g. `PreconditionsTest`'s `*_NotDebug`). |

## Tests

Test scenarios (every NUnit test and test case in `NodaTime.Test` and `NodaTime.TzdbCompiler.Test`, with arguments) are extracted by
`tools/NodaJs.Tools (scenarios)` into `test/scenarios/**/*.generated.ts`. A hand-ported test file
supplies the test *body* for each NodaTime test method, and the harness runs it over every extracted
case; methods without a body show up as `todo`. See `test/README.md`.
